# 24 — Response Note Cryptographic and Key-Lifecycle Protocol

## Status

**OWNER-APPROVED — project-owner decision recorded on 2026-08-25;
independent cryptographic/protocol review remains required. No Response Note
encryption, finalization, recovery-decryption, or Response-DEK operation is
authorized for production by this document alone.**

This proposal selects the exact version-1 Response Note byte profile, AEAD
construction, nonce and AAD rules, fixed-length ciphertext envelope,
non-exportable Response-DEK model, first-read expiry sequence, replay controls,
and failure behavior. It does not approve a Key Service product, topology,
HSM, service-authentication mechanism, step-up construction, database
durability profile, deployment, or reporter endpoint.

## Governing requirements

This proposal applies primarily to:

- `SEC-CONF-001..008`;
- `SEC-LOG-004..005`, `SEC-LOG-009..012`;
- `SEC-ACCESS-010..015`;
- `SEC-AUTH-002`, `SEC-AUTH-005..007`;
- `SEC-DEL-001..006`;
- `SEC-KEY-001..007`;
- `SEC-RECOVERY-001..005`;
- `SEC-RESPONSE-001..008`;
- `SEC-FINALIZE-001..006`;
- `SEC-BROWSER-001..002`.

`docs/01_SECURITY_BASELINE.md`, the finalization sequence in `docs/03`, the
credential construction in `docs/21`, and the audit protocol in `docs/23`
remain authoritative. A conflict stops implementation and returns the decision
to the project owner.

## Security outcome

Version 1 must provide all of these properties:

1. every Response Note has one independently random 256-bit Response-DEK;
2. the Recovery Secret never derives, encrypts, wraps, or reconstructs that DEK;
3. application/database/blob compromise does not reveal the DEK;
4. ciphertext modification or substitution fails authentication before any
   plaintext is released;
5. exact immutable report/response/finalization/key context is authenticated as
   AAD;
6. stored ciphertext length does not reveal Response Note length inside the
   approved 5,000-character range;
7. concurrent first reads set one immutable 72-hour expiry and never extend it;
8. Key Service time enforcement denies every use after expiry even while state,
   replica, or ciphertext cleanup is incomplete;
9. destruction across every live replica and every supported restore prevents
   later recovery.

Property 9 cannot be established by document review alone. The Key Service
product/topology proof of concept remains a release-blocking gate.

## Selected construction; no invented primitive

The version-1 AEAD is libsodium
`crypto_aead_xchacha20poly1305_ietf_*` in combined mode:

- 256-bit key;
- 192-bit public nonce;
- 128-bit authentication tag appended to the ciphertext;
- authenticated additional data;
- no compression and no detached tag.

Every key and nonce is generated by the Key Service using libsodium's operating
system-backed CSPRNG. A Response-DEK encrypts exactly one version-1 Response
Note envelope. Retry returns the original stored envelope; it never encrypts a
second time with that key.

XChaCha20-Poly1305 is a documented libsodium construction rather than an IETF
Standards Track algorithm. Its 192-bit nonce permits random nonce generation,
and libsodium recommends it where cross-library interoperability is not
required. This deliberate choice, the pinned libsodium/PyNaCl versions, binary
provenance, platform support, and test vectors require independent review.

There is no algorithm negotiation, automatic migration, AES fallback,
plaintext mode, development key, or caller-selected algorithm. A future
algorithm requires a new format version and reviewed migration that never
decrypts under ambiguous context.

## Exact plain-text byte profile

Before step-up authorization, the Operator Console creates one final preview
and canonicalizes the Response Note exactly once:

1. accept Unicode scalar values only; reject unpaired surrogates and U+0000;
2. normalize CRLF and CR line endings to LF;
3. normalize Unicode to NFC;
4. enforce at most 5,000 Unicode scalar values after normalization;
5. encode with strict UTF-8 without BOM;
6. enforce at most 20,000 UTF-8 bytes;
7. apply the separately approved plain-text/no-active-link content policy;
8. freeze those exact bytes before CAPTCHA, step-up, and audit binding.

The final preview must show the canonical form. No later layer may trim,
normalize, re-encode, template-expand, translate, auto-link, or otherwise alter
the frozen bytes. The exact step-up artifact-binding construction remains a
separate OPEN decision and must bind these bytes and their operation context.

The fixed-size plaintext frame is exactly 20,005 bytes:

```text
response-plaintext-frame-v1 =
    0x01
 || uint32-big-endian(utf8-byte-length)
 || canonical-utf8-response-note
 || zero-padding-to-exactly-20,005-bytes
```

The length is in the range 0 through 20,000. Every byte after the declared text
must be zero. A decryptor rejects a wrong total length, impossible declared
length, nonzero padding, invalid UTF-8, non-NFC text, disallowed scalar, or
post-decryption character count above 5,000. It never returns partial text.

Fixed framing hides the note length from the report database/blob-store threat
boundary. It does not hide the existence of a Response Note, access timing, or
traffic sizes outside the controlled application boundary.

## Immutable identifiers and AAD

The state authority generates random, internal 16-byte identifiers for:

- `report-id`;
- `response-id`;
- `finalization-id`.

The Key Service generates a random opaque 32-byte `response-key-handle`. The
handle is not key material or authorization. None of these values is a public
Ticket ID, Recovery Secret, username, URL value, or reporter-supplied value.

The exact RFC 8949 deterministic-CBOR AAD is:

```text
response-aad-v1 = [
  version: 1,
  purpose: "RESPONSE_NOTE",
  algorithm: 1,                  ; XCHACHA20_POLY1305_IETF
  content-profile: 1,            ; canonical UTF-8 fixed frame
  report-id: bstr .size 16,
  response-id: bstr .size 16,
  finalization-id: bstr .size 16,
  response-key-handle: bstr .size 32,
  plaintext-frame-length: 20005
]
```

The AAD contains immutable context only. Mutable report state, lease time, and
expiry do not enter it; those are authorization checks. The Key Service derives
the AAD from authenticated typed fields and does not accept caller-supplied raw
AAD bytes.

## Exact ciphertext envelope

The Key Service returns deterministic CBOR matching:

```text
response-ciphertext-envelope-v1 = [
  version: 1,
  algorithm: 1,
  content-profile: 1,
  report-id: bstr .size 16,
  response-id: bstr .size 16,
  finalization-id: bstr .size 16,
  response-key-handle: bstr .size 32,
  nonce: bstr .size 24,
  ciphertext-and-tag: bstr .size 20021
]
```

`ciphertext-and-tag` is the combined-mode output over the 20,005-byte frame
with the exact AAD above. Unknown versions/algorithms/profiles, alternate CBOR,
wrong types/lengths, extra fields, trailing bytes, inconsistent identifiers,
or a tag failure are rejected before plaintext release.

The exact envelope bytes are stored in PostgreSQL with the response metadata so
the ciphertext and transition to `FINALIZING` can commit in one database
transaction as required by the approved finalization protocol. It is never
stored as a user-controlled path or ordinary downloadable object.

## Response-DEK representation and negative capability

The Response-DEK is 32 independently random bytes generated inside the Key
Service. It is not derived from:

- Ticket ID or Recovery Secret;
- report/response/finalization identifiers;
- Response Note bytes or ciphertext;
- Report-DEK or another Response-DEK;
- Django `SECRET_KEY`, verifier, audit, CAPTCHA, TLS, export, or service keys.

The application stores only the opaque `response-key-handle`; it stores no
plaintext, wrapped, encrypted, derived, escrowed, cached, or backup copy of the
Response-DEK. The supported Key Service performs AEAD operations inside its own
trust domain and never exports the key to Django, workers, operators,
administrators, recovery code, databases, or blob storage.

If the selected Key Service internally wraps or encrypts live key objects, that
representation is part of the Key Service trust domain and remains subject to
`SEC-KEY-002..004` and `SEC-KEY-007`. It must not enter historical backups or
combine with retained infrastructure material to resurrect a destroyed key.
The exact internal wrapping/HSM construction is therefore a product/topology
gate, not an application ciphertext field.

## Narrow Key Service operations

Version 1 permits only these response-key operations:

- `CREATE_AND_ENCRYPT_RESPONSE` — create one provisional Response-DEK and exact
  envelope for one fenced finalization;
- `VERIFY_RESPONSE_ENVELOPE` — authenticate the exact stored envelope without
  returning plaintext;
- `ACTIVATE_RESPONSE_KEY` — make the key eligible only for future authorized
  reporter recovery after matching `FINALIZING` state is committed;
- `ARM_RESPONSE_EXPIRY` — set one immutable absolute Key Service expiry before
  the first plaintext release;
- `DECRYPT_RESPONSE` — return plaintext only for one valid recovery request
  inside the armed window;
- `DESTROY_RESPONSE_KEY` — irreversibly destroy the key across every supported
  live replica and return durable controlled evidence.

There is no `GET_KEY`, `EXPORT_KEY`, `UNWRAP_ANY`, `DECRYPT_ANY`, caller-chosen
handle, administrator recovery, expiry extension, key recreation, or state
bypass operation.

Each call requires authenticated service identity, exact operation, internal
identifiers, current state/version, idempotency ID, action nonce, and the
applicable audit receipt. Lease generation and step-up artifact binding are
mandatory for finalization operations. Recovery operations require the
separately authenticated recovery authorization; the Recovery Secret itself is
never sent to or stored by the Key Service.

## Finalization staging and activation

The proposal refines step 5 of the approved finalization protocol without
claiming a distributed transaction:

1. validate the current OPEN lease/version, CAPTCHA, exact-artifact step-up,
   and `FINALIZATION_REQUESTED` receipt;
2. call `CREATE_AND_ENCRYPT_RESPONSE` with one random `finalization-id` and
   operation idempotency context;
3. the Key Service creates a `PROVISIONAL` non-decryptable key object, stores
   only the minimum idempotency/binding metadata, and returns the exact envelope;
4. revalidate and lock report/lease state;
5. in one PostgreSQL transaction, store the exact envelope and immutable
   identifiers, consume the finalization authorization, increment the state
   version, and enter `FINALIZING`;
6. authenticate the stored envelope with `VERIFY_RESPONSE_ENVELOPE`;
7. call `ACTIVATE_RESPONSE_KEY`; the Key Service independently verifies the
   matching committed `FINALIZING` context before activation;
8. only then may the existing approved Report-DEK destruction sequence resume.

An identical create retry returns the byte-identical envelope and same handle.
A different request, artifact binding, state version, nonce, or finalization ID
cannot reuse the operation.

If PostgreSQL never commits the matching `FINALIZING` record, the provisional
key is never recovery-usable. A reconciler asks the state authority whether an
exact committed binding exists: it activates a matching committed binding or
destroys a definitively orphaned key. Ambiguous/unavailable state keeps the key
inert and raises controlled operational evidence; it does not guess, activate,
or destroy. The Key Service stores no plaintext response draft.

After `FINALIZING` commits, ordinary operator access, editing, reopening, and
export remain terminated. Failure to activate or verify does not expose the
response or permit different response bytes. Report-DEK destruction cannot
start until the exact response envelope and active Response-DEK are verified.

## Recovery authorization and first-read expiry

Ticket ID and Recovery Secret validation remains exactly the owner-approved
`docs/21` construction and occurs in the Recovery Gateway/verifier boundary.
The Key Service receives only an opaque successful recovery-authorization
reference bound to the internal report/response, operation, nonce, and expiry.

For every valid retrieval request:

1. validate POST, no-JavaScript challenge, recovery credentials, current
   response eligibility, rate limits, and generic external response behavior;
2. append `RESPONSE_RETRIEVAL_REQUESTED` and obtain the exact `docs/23` receipt;
3. lock the response row and validate state/version using PostgreSQL server
   time;
4. if `first_read_at` is null, set it to that transaction's server time, set
   immutable `response_expires_at = first_read_at + 72 hours`, move to
   `READ_WINDOW`, increment version, and commit exactly once;
5. if already in `READ_WINDOW`, reuse the existing timestamp and expiry without
   modification;
6. call `ARM_RESPONSE_EXPIRY` idempotently with the exact committed expiry;
7. only after the Key Service confirms the same immutable expiry, call
   `DECRYPT_RESPONSE` with the current state/version, recovery authorization,
   receipt, idempotency ID, and nonce;
8. validate the decrypted fixed frame completely, then return only canonical
   plain text with `no-store`/`no-referrer` protections and no active links;
9. append the truthful completed or failed outcome without copying any reporter
   input, credential, plaintext, or raw error.

"First successful read" is defined as the first valid recovery authorization
that durably establishes the read window before decryption. The server cannot
prove that a browser received, displayed, or saved the response. A crash,
disconnect, or Key Service failure after step 4 does not roll back or extend
the 72-hour window. This confidentiality-first availability trade-off requires
explicit owner approval.

The Key Service uses its approved clock and denies at or after its armed expiry
without relying on later database cleanup. If the state authority presents an
earlier valid expiry, the earlier boundary wins. A mismatch, extension attempt,
clock regression, or unavailable trusted time fails closed and alerts with
controlled metadata.

## Expiry and destruction

At or after `response_expires_at`:

1. Recovery Gateway and Key Service deny every decrypt immediately;
2. the workflow uses a fenced, idempotent expiry operation and durable audit
   receipt;
3. Key Service destroys the Response-DEK across every supported live replica;
4. durable destruction evidence is recorded truthfully;
5. recovery verifier/state is invalidated so credentials cannot authorize use;
6. response state becomes `EXPIRED`/destroyed according to the approved model;
7. physical ciphertext deletion proceeds separately with retry and alerting.

Delayed state cleanup, stale replicas, rollback, backup restore, or retained
ciphertext never extends use or recreates the key. An unknown result after a
possibly completed destruction is resolved only forward: never recreate a key
or return plaintext.

The current rule for a never-read Response Note is unchanged: no 72-hour clock
starts. Its maximum unread retention remains a separate OPEN HIGH decision.

`docs/32_RETENTION_AND_DELETION_PROTOCOL.md` resolves that design item
with a 90-day unread deadline and one narrow pre-deadline conversion to the
existing full 72-hour read window. The change was owner-approved on 2026-08-26
but remains non-authorizing pending legal/operational and independent review
and every named production gate.

## Atomicity, concurrency, and replay

PostgreSQL uniqueness and locked/conditional transitions must enforce:

- one `response-id` and one `finalization-id` per report finalization;
- one exact ciphertext envelope per response;
- one immutable transition from null `first_read_at` to `READ_WINDOW`;
- one immutable `response_expires_at`;
- no finalization/export/deletion race winner outside the approved state graph;
- no use of a stale report state, state version, lease ID, or lease generation.

Key Service uniqueness must independently enforce one response key per
`response-id`/`finalization-id`, one create result per idempotency context, one
expiry value, and monotonic `PROVISIONAL -> ACTIVE -> EXPIRY_ARMED -> DESTROYED`
transitions. `DESTROYED` has no reverse edge.

Browser/session state, application cache, in-memory locks, Celery task identity,
or pre-check queries are never authoritative. SQLite and one-process tests do
not prove these properties.

## Persisted and prohibited data

| Data | Permitted persistence | Prohibited persistence/exposure |
|---|---|---|
| Canonical Response Note | No durable plaintext; transient finalization/recovery memory only | DB, blob, queue, logs, audit, trace, exception, server-side draft |
| Fixed ciphertext envelope | PostgreSQL response row, immutable | Public URL, ordinary download, mutable replacement |
| Response-DEK | Live Key Service object only | Django/DB/blob/cache/queue/log/audit/backup/export |
| Response key handle | Typed internal metadata | URL, reporter UI, authorization by possession, logs |
| Ticket ID | Approved lookup storage | Key derivation, audit correlation beyond approved internal mapping |
| Recovery Secret | Transient verifier input only | Key Service, plaintext storage, URL, logs, admin recovery |
| Recovery verifier | Approved keyed verifier state | Plain secret or cross-purpose key use |
| First-read/expiry times | Controlled server metadata | Client-selected or sliding values |
| Artifact binding | Opaque approved 32-byte binding | Plain guessable note digest in permanent audit |

Plaintext buffers are bounded and short-lived. The implementation minimizes
copies and uses library-supported secure memory where practical, but does not
claim deterministic zeroization of every Python/runtime/browser copy.

## Failure behavior

| Failure | Required result |
|---|---|
| Canonicalization/profile failure | Reject before finalization; no weaker encoding |
| CAPTCHA, step-up, audit, lease, or state failure | No Response-DEK or protected response persistence |
| Key Service unavailable | No local encryption/decryption fallback |
| Create reply lost | Retry exact idempotency context; return byte-identical result only |
| PostgreSQL commit fails after provisional create | Never activate; reconcile and destroy when absence is definitive |
| State unavailable during provisional reconciliation | Keep key inert; do not guess or expose plaintext |
| Envelope verification/tag/context failure | Stop finalization or retrieval and alert with controlled metadata |
| Activation fails after `FINALIZING` commit | Keep response invisible and resume exact binding only |
| Concurrent first reads | One database winner fixes expiry; all valid losers reuse it |
| Crash after first-read commit but before plaintext response | Window remains started and non-sliding |
| Expiry-arm mismatch or extension attempt | Deny and alert; never extend |
| Decrypt failure | Generic external non-success; no partial plaintext or oracle detail |
| Key destruction uncertain | Deny all use and resolve forward; never recreate |
| Ciphertext deletion failure after destruction | Key stays destroyed; retry physical deletion and alert |
| Restore contains old key/ciphertext | Key remains unusable; release-blocking restore test fails otherwise |

## Required tests before enablement

At minimum, release-blocking tests must prove:

- pinned libsodium/PyNaCl XChaCha20-Poly1305 vectors and independent
  cross-implementation fixtures;
- exact key/nonce/tag sizes and combined-mode ciphertext length;
- RFC 8949 deterministic AAD/envelope bytes and closed-schema rejection;
- nonce uniqueness, one encryption per key, byte-identical idempotent retry, and
  no application-generated or caller-selected key/nonce;
- bit changes and cross-report/response/finalization/key-handle substitution
  fail authentication before plaintext release;
- every valid note length from 0 through 5,000 scalar values produces the same
  20,021-byte ciphertext-and-tag length;
- line-ending/NFC/UTF-8 canonicalization and rejection of invalid scalars,
  nonzero padding, invalid frame lengths, invalid UTF-8, and over-limit text;
- the application never receives or persists Response-DEK material and no
  public/general decrypt endpoint exists;
- crash injection at every finalization staging/activation boundary reaches
  only the documented state and never destroys the Report-DEK early;
- 20–100 synchronized PostgreSQL/process retrievals establish one immutable
  `first_read_at` and expiry;
- retries, stale versions, reused nonces, wrong receipts, wrong recovery
  authorization, and cross-ticket attempts fail closed;
- Key Service denies exactly at expiry even when PostgreSQL, workers, or cleanup
  are unavailable, delayed, rolled back, or stale;
- destroy propagation, delayed replica, snapshot/restore, rollback, disaster
  recovery, and combined-backup tests cannot resurrect a Response-DEK;
- ciphertext remains reporter-invisible until confirmed Report-DEK destruction
  and durable `REPORT_KEY_DESTROYED` evidence;
- no plaintext, secret, key, note digest, or raw error enters logs, audit,
  alerts, metrics, traces, temporary files, queues, or browser persistence.

SQLite, ordinary Django `TestCase`, one process, a mock Key Service, or a
software-only deletion assertion is insufficient for release acceptance.

## Recorded project-owner decision

On 2026-08-25 the project owner approved all six visible choices:

1. XChaCha20-Poly1305-IETF combined mode with one random 256-bit Response-DEK
   and one random 192-bit nonce per immutable Response Note;
2. NFC/LF/strict-UTF-8 canonicalization, 5,000-scalar/20,000-byte limits, and
   constant 20,005-byte zero-padded plaintext framing;
3. deterministic-CBOR AAD/envelope schemas and authenticated immutable context;
4. the non-exportable Key Service AEAD model, with no application-stored wrapped
   Response-DEK and inert provisional-to-active staging;
5. first valid recovery authorization starts the non-sliding 72-hour window
   before decrypt, including the accepted lost-response availability risk;
6. Key Service hard expiry, forward-only destruction, and the stated
   concurrency/idempotency behavior.

Independent cryptographic/protocol review remains mandatory. Production
remains blocked by the exact step-up artifact binding,
Key Service product/topology/HSM and non-resurrection proof, service
authentication, trusted-clock profile, PostgreSQL concurrency/durability,
audit implementation/review, recovery endpoint, and deployment review.

## Stage A inert implementation evidence

The current implementation may validate only static Response Note crypto
profile shapes and return content-free descriptors for the approved version,
algorithm, content profile, fixed sizes, immutable context-size profile,
AAD-purpose label, and allowlisted Response-DEK operation names.

The Stage A descriptor and its non-executing source policy do not canonicalize
Response Note text, create plaintext frames, encode or parse deterministic
CBOR, encrypt, decrypt, compare tags, generate random material, retain nonce,
AAD, ciphertext, key-handle, or Response-DEK values, persist protected bytes,
call a Key Service, consume recovery authorization, use audit receipts, inspect
state rows, expose endpoints, or authorize response use.
