# 05 — Recovery Credentials and Response Note

## Goal

Allow a reporter to return later and read exactly one Response Note without an account, email address, phone number, or authenticated identity.

## Current owner-approved credential model

The exact encoding and verifier choices in
`docs/21_RECOVERY_CREDENTIAL_CONSTRUCTION.md` are owner-approved. They remain
OPEN CRITICAL for implementation until the required independent cryptographic
review is complete.

Use two independently generated values:

1. **Ticket ID**
   - high-entropy random public lookup identifier;
   - not sequential;
   - not treated as an authentication secret.

2. **Recovery Secret**
   - 256 bits generated by a CSPRNG;
   - security of access depends on this secret;
   - never derived from timestamp, ticket content, IP, username, or Ticket ID.

No additional six-digit PIN is currently recommended because it adds little security compared with a 256-bit random secret and increases UX/error complexity.

## Example reporter UX

After successful submission:

```text
Segnalazione inviata correttamente

TICKET ID
JQXMTWKNPAEZRHGCFVYSKLPDRA

RECOVERY SECRET
w9Nc2XL1z3yK_j8Bq6VnUFu4ePA5cG7WTkM0rSDYqZE

Conserva entrambi i valori.
Il Recovery Secret viene mostrato una sola volta.
Senza questi dati non potrai leggere la risposta.
```

The exact displayed encoding is owner-approved in
`docs/21_RECOVERY_CREDENTIAL_CONSTRUCTION.md` but remains implementation-gated
by independent cryptographic review.

## Display-once rule

The Recovery Secret must be presented in one explicit post-submission moment only.

It must not be recoverable through:

- navigating back;
- reloading the confirmation endpoint;
- a "forgot secret" function;
- email;
- administrator lookup.

Reporter pages must use no-store/no-referrer protections.

The platform cannot guarantee that malware or a compromised browser does not copy what is displayed.

## Reporter storage UX

Baseline should not automatically:

- email the credentials;
- send SMS;
- upload them to cloud storage;
- generate persistent browser storage;
- automatically download a local file.

The reporter decides where to store them.

A local copy button may be provided when JavaScript is available, but no-JS operation should remain possible.

## Retrieval

Reporter visits a neutral check page and submits via POST:

- Ticket ID;
- Recovery Secret;
- CAPTCHA.

Secrets MUST NOT be placed in URLs or query strings.

## Enumeration resistance

Invalid combinations and existing-but-not-ready combinations must be externally indistinguishable as far as reasonably practical.

Do not reveal:

- whether Ticket ID exists;
- whether the secret is wrong;
- whether the ticket has not yet been answered;
- whether a former response expired.

Use a generic result for non-success states.

Timing and code paths should be designed to reduce easy oracle differences.

## Server verification storage

The Recovery Secret should not be stored in plaintext.

A candidate pattern is a keyed verifier such as:

`HMAC(server_verification_key, ticket_id || recovery_secret)`

The final construction must be reviewed before implementation.

The verifier key must be purpose-separated from Django `SECRET_KEY`, encryption keys, audit keys, and export keys. Exact message framing/domain separation, key lifecycle, and rotation behavior remain part of the OPEN verifier decision.

## Collision handling

Ticket IDs must have a database uniqueness constraint.

If random Ticket ID generation collides, regenerate.

Recovery Secret collisions are already astronomically unlikely at 256 bits.

A duplicated Recovery Secret alone must not grant access to another ticket because the Ticket ID is also required.

## Response Note properties

- plain text only;
- maximum 5,000 characters;
- no HTML;
- no images;
- no attachments;
- no active links;
- URLs should not be automatically linkified;
- immutable after publication;
- no server-side draft in the baseline.

## Response Note encryption and Response-DEK

Every Response Note has an independent `Response-DEK`.

Conceptually:

```text
Ticket ID + Recovery Secret
  -> authorize recovery
  -> allow the system to make the applicable Response-DEK usable
  -> Response-DEK decrypts the Response Note ciphertext
```

The Recovery Secret must not be the sole material sufficient to decrypt a retained or restored ciphertext indefinitely.

The exact credential verifier is owner-approved in `docs/21`.
`docs/24_RESPONSE_NOTE_CRYPTOGRAPHIC_PROTOCOL.md` defines the owner-approved AEAD, nonce,
AAD, constant-length envelope, non-exportable Response-DEK representation,
staging, and expiry lifecycle. It remains OPEN CRITICAL and no implementation
may anticipate its independent review or production gates.

## Response retention

At first successful reporter read:

- record `first_read_at` using server-side time;
- define expiry at first read + 72 hours.

The owner-approved `docs/24` protocol defines this boundary as the first valid
recovery authorization that durably establishes the window before plaintext
decryption. The project owner accepted that availability trade-off on
2026-08-25.

Concurrent first-read attempts must use server-authoritative locking/conditional update so exactly one immutable `first_read_at` and expiry are established. Later reads reuse that expiry and cannot extend it.

During those 72 hours, the same valid recovery credentials may re-open the same Response Note.

After 72 hours:

- refuse every further recovery/Response-DEK use based on server-authoritative expiry;
- destroy the Response-DEK across every supported replica;
- make every residual/backup copy of the ciphertext unusable;
- invalidate/remove recovery verifier/state as appropriate;
- retry physical ciphertext deletion separately.

Response-DEK destruction is subject to the same non-resurrection release gate as Report-DEK destruction.

If the reporter never reads the Response Note, the current business rule does not start the 72-hour countdown.

Long-term retention of never-read Response Notes remains an operational risk to revisit.

## Display-once guarantee boundary

The server guarantees that it will not emit the Recovery Secret a second time after the one explicit post-submission response. `no-store` and `no-referrer` controls are mandatory.

The platform does not claim that it can erase a secret already rendered by a browser from screenshots, clipboard, browser memory, device swap, malware, or every browser history implementation.
